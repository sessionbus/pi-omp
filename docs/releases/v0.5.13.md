# pi-omp v0.5.13

`pi-peer` and `omp-peer` remain **preview** integrations.

## Requirements

- **Sessionbus:** v0.5.9 or newer (daemon and hub), as for v0.5.12. The Sessionbus Go SDK stays pinned at `v0.5.9`, and the bundled `@sessionbus/kit` is 0.5.12.
- **Native Pi, OMP and Bun:** installed separately and not pinned.
  - **Final code** (commit `5794951`; later commits change only documentation): on one Linux host, each once, an interactive idle wake and a lane Run passed with Pi 1.5.1 (Node 25.3.0), and the same two with OMP 18.18.6 (Bun 1.4.4). Each interactive check ended with an ordinary quit. Quitting with peer messages waiting, session switch, busy steering and the owner's matrix were not run on that code; Pi 1.5.1's quit and session-switch behaviour was checked against its source.
  - **Earlier build `eebdc82`**, with Pi 1.5.0, OMP 18.18.5 and Bun 1.4.4, on Linux and the Mac: scoped interactive and lane checks, including Pi interactive idle and busy delivery, OMP busy steering and lane Runs.
  - **Earlier build `a2faf74`:** the owner's matrix ran with Pi 1.3.0, OMP 18.12.2 and Bun 1.4.3. A smoke check on the Mac (Pi 1.4.0, OMP 18.13.1, Bun 1.4.4) passed, and one on UMKA (OMP 18.13.2) found the late-binding defect fixed below.
  - The checks and their limits are listed in the release PR.
- **OMP lanes:** need Oh My Pi 18.11.0 or newer. A lane Run ends at OMP's own `prompt_result` for the lane's prompt; older versions do not send it for agent work, so there a lane Run waits until it is cancelled.

## Changes since v0.5.12

### Pi

- **Direct peer.** The lane bridge moved to an inherited socket pair, and interactive ownership moved into the native extension.
- **Pi 1.2.0.** The settled drain accepts Pi's deferred send. A failed tool call keeps the session. Pi's `mcp` command passes through to native Pi.
- **Busy steering.** A peer message that arrives while a lane's Run or an interactive task is running is steered into that task. A lane steer is bound to its Run, and Pi's own work stays out of it.
- **Takeover.** A superseded interactive Pi keeps running without Sessionbus. The bundled kit 0.5.12 keeps a crossing reply from ending Pi.
- **Escape.** A steered peer message that an aborted task never read is kept in the session history.
- **Unread steers without an abort.** The same holds when a task ends without an abort and leaves a steered peer message unread (Alt+Up, a failed compaction-queue flush, or a task that cannot continue), and when you quit Pi. Peer messages queued for Pi's next task are written to history at quit too, after those, in arrival order, and no new task starts while Pi quits. If a task (or a compaction) is still running at quit while such a message or a queued peer message waits, the extension aborts it and waits up to 2 seconds for Pi to settle before writing; past that, nothing is written. Leaving a session for another one (`/new`, `/resume` or `/fork`) does the same for the session being left: its unread steered peer messages and those queued for its next task are written to its history, and the new session receives peer messages normally. Both quit and session switch have one exception; see "Pi quit or session switch while another extension finishes a task" under [Known open items](#known-open-items).
- **Prompt refused before Pi.** A blank lane prompt, or one that exceeds the 1 MiB native input frame once JSON-encoded, now ends only its Run, and the lane stays. Before, the lane ended.
- **Pi 1.3.0.**
  - The `sessionbus` tool stays active when Pi restores a resumed session's recorded tool set.
  - `--tools` lists of `+name`/`-name` modifiers pass through the managed launch guard.
  - The guard matches `--tools` and `--exclude-tools` entries as Pi does, as exact names or `*` patterns: an exclusion such as `session*` is refused, and an allowlist pattern such as `*` that matches `sessionbus` passes.

### OMP

- **Lane Run boundary.** A lane Run ends at OMP's own `prompt_result` for the lane's prompt; later work by OMP is its own.
- **Busy steering.** A peer message that arrives while a lane's Run is active is steered into it (`injected`). Interactive deliveries get the receipt of their hand-off: `injected` while OMP is busy, `written` while it is idle.
- **Context order.** Interactive delivery accepts OMP's context hook before the delivery's own message events.
- **Bun.** A lane started by the Sessionbus service finds Bun in its standard install location when the service `PATH` lacks it: `$BUN_INSTALL/bin/bun`, else `~/.bun/bin/bun`.
- **File mentions.** In a peer message that starts a lane Run, an invisible word joiner (U+2060) is placed right before each `@` that OMP would read as a file mention. OMP then reads no file the peer names, and the visible text is unchanged. The owner's own Run input is sent as given.
- **Request-time prompt failure.** OMP can admit a prompt and then fail it before its run, for example with no model or no API key. That now ends only the Run: it is `unavailable` with OMP's text, and the lane stays. Before, the lane ended. A prompt that our own validation refuses (empty or over the native bound) also ends only the Run.
- **Prompt ended before its run.** OMP can also end an admitted lane prompt before any run while reporting it as invoked: a usage-limit denial, and on 18.13.x a reached cost cap. That now ends only the Run, with OMP's text when it gives one, and the lane stays. Before, the lane ended.
- **Encoded prompt size.** A lane prompt that exceeds the 1 MiB native input frame once JSON-encoded (escaping can grow it, and a peer message's rendering adds to it) is never written: only the Run fails, with that reason, and the lane stays. Before, the lane ended. The same holds for Pi.
- **Late extension binding (OMP 18.13.1 and later).** OMP can bind the managed extension after an interactive launch's first frame; it then saw a delivery's `message_end` before its `message_start` and ended the user's session. That order is now accepted. A delivery whose native events no longer match what was sent, or one pending when you `/clear` the session, ends only that delivery's attempt: its receipt stays, it is not sent again, and the session stays connected.

## Known open items

These items remain open.

- **OMP Escape.** Escape during OMP's working animation returns a steered peer message that OMP had not read to the editor, where it is neither sent nor kept in history unless submitted; its receipt stays `injected`. This is an open defect for the planned OMP rework; see the [OMP guide](../../omp/README.md).
- **No failure reason for a started Run.** A Run that a provider error ends after OMP's run started is `done`, outcome `failed`, native stop reason `error`, without OMP's error text. The Run terminal has no field for a failure reason.
- **Late steer.** A peer message that OMP queues after the task's last steering check is answered by OMP's own continuation, outside the Run's result.
- **Delayed delivery (OMP lanes).** Peer messages for a lane Run can be delivered to a later Run: after OMP takes a first queued peer message into the running task (it reports that as a new `before_agent_start`), or when another extension is slow to handle `agent_end` and OMP's end of the previous Run reaches the managed extension after the next Run started. Nothing is lost and no receipt is wrong.
- **OMP lane steer limit.** A steer that OMP carries unread into the next Run no longer counts against the lane's steer limit there, so OMP can briefly hold more unread steers than the limit. OMP reports no event for a steer it drops or carries.
- **Pi forwarded lane prompt.** When an input extension forwards a lane Run's prompt and that forwarded prompt fails before its run starts, or handles the prompt before any preflight of ours, the Run is unavailable and the lane stays. Another extension's failed `sendUserMessage` in that same short window also ends the Run as unavailable. If an extension handles a prompt and forwards it so late that its preflight comes after the next Run recorded its input, the next Run can take it: Pi's preflight carries no prompt identity. The extension received the input in these cases, so it is not replayed and a message that started the Run gets an uncertain receipt; the extension may still run that prompt later, so a caller's retry can repeat its effects. An interrupt while an owned dialog's cancellation is still being written waits for that write.
- **Pi deferred delivery.** A peer delivery accepted while another extension's settled handler runs can be lost if an earlier deferred Pi action fails (a Pi defect, reported as [earendil-works/pi#11955](https://github.com/earendil-works/pi/issues/11955)). Pi runs the actions deferred during a settle one after another without catching each one's error, so one failing action drops the later ones (Pi 1.4.0 `agent-session.js:683-706`; the same code is in Pi 1.5.0 and 1.5.1).
- **Pi quit or session switch while another extension finishes a task — OPEN DEFECT.** If another installed Pi extension handles the end of a task with slow work, Pi holds the peer messages this extension hands it in that time: messages waiting for Pi's next task, and any arriving then. If you quit or switch sessions (`/new`, `/resume` or `/fork`) in that time, or while a task is running, these messages are not reliably saved to the history of the session being left. Each can instead start its own task there, one after another, with your normal Pi permissions. If a task was running, Pi stops it and runs the first of these tasks to its end before the session ends; after an ordinary quit, Pi's screen is already closed by then. Some accepted messages can be lost, with no delivery and no history entry, although their senders were told they were written or queued. After a session switch, what happens to the remaining ones in the session being left was not verified. After Escape, such messages can start several separate tasks instead of one. Without quit or a session switch there is no shutdown-loss path, but the separate deferred-start failure (Pi issue #11955, above) still applies. Unread steered peer messages are not affected. This was found by reading the source of Pi 1.5.1 and 1.5.2 for quit, and of Pi 1.5.0, 1.5.1 and 1.5.2 for a session switch; it has not been reproduced live, and its frequency is unknown.
