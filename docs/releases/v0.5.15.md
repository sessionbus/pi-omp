# pi-omp v0.5.15

`pi-peer` and `omp-peer` remain **preview** integrations.

## Release preparation correction

The v0.5.14 release remains unpublished: its release workflow stopped on the OMP
own-work dialog cancellation test. This release settles the test's initial
negotiation write before filling its queue, preserving the original failure
assertions. Forced ordering demonstrated the old fixture failure and the
corrected pass; removing the lane-loss behavior still failed the corrected
test. This does not establish the exact schedule of the earlier CI failures.

Product implementation is unchanged from that tag. This release also adopts
the Go SDK and JavaScript kit 0.5.16 described below. The native observations below
retain their original e36e installation identity. They were not repeated for
the new version label.

## File transfer in interactive sessions and lanes

Both products expose the same complete Sessionbus tool declaration as Codex,
including `transfer.offer`, `transfer.request`, `transfer.accept`,
`transfer.cancel` and `transfer.status`. The shared declaration is vendored
without changing its description or argument fields.

The Go SDK and bundled `@sessionbus/kit` are v0.5.16. File transfer requires
v0.5.14 daemons on the participating hosts and a transfer-capable recipient.
Older peers can still exchange ordinary messages; they cannot receive files.

Local paths use the executing native session's working directory, including
managed lanes and OMP native Task children. The adapter preserves symlink and
`..` spelling. Absolute paths are unchanged; relative paths are refused when
the native working directory is unknown.

Transfers use the SDK's direct filesystem access as the OS user. They do not
use the native sandbox or ask for native approval per path. Tightening
transfer permissions remains open and is not a release gate.

OMP's existing public connection attempts now own their SDK transfer manager
and bound caller. Machine transfer requests stay on the connection reader;
completion notices are projected on the existing ordered delivery worker.
The existing retained-byte limit also covers the projected notice. Closing
an attempt joins its transfer cleanup before the next connection attempt.
Pi interactive peers and both lane Workers use their existing SDK owners.

The updated SDK also reports `not_responding` host availability in list
results and negotiated federation-policy refusals.

## Existing limitations and evidence

The [v0.5.13 known open items](v0.5.13.md#known-open-items) remain open. In
particular, Pi's slow-extension quit/session-switch race can start multiple
tasks and lose accepted peer messages without a history entry; transfer
notices use the same delivery path. This release does not change that race
or perform the separately planned OMP rework.

Native acceptance results and exact tested versions are recorded in
[PR #12](https://github.com/sessionbus/pi-omp/pull/12). Earlier native checks listed in v0.5.13 remain evidence for
those earlier builds, not fresh transfer acceptance for this release.

## Native transfer observations

On Linux UMKA, the permanent e36e installation was exercised with Pi 1.5.1
(deepseek-flash, high) and OMP 18.18.6 (the native fallback to
DeepSeek V4 Pro, high). The later README correction changes no runtime bytes.
Both products completed interactive offer/accept and an idle lane's
request/accept with matching 1 MiB file hashes. Cancellation, refusal to
overwrite an existing file, explicit overwrite and an absent-ID status
refusal followed by ordinary tool use were observed.

A 1 GiB stream kept each lane connected beyond its 1000 ms post-Run grace.
Closing the lane cancelled the transfer; no partial destination or temporary
file remained. Pi needed one bounded repeat because its first lane
waited for full transfer completion before ending its Run; that first file
completed correctly and was preserved. OMP exercised the hold on its first
attempt. All owned test lanes and TUIs exited, with zero transfer temporary
files in the fixture directories.

Pi noticed an injected busy message within the original task but declined the
requested acknowledgment; this is not an acknowledgment pass. OMP admitted
its marker while generating the final response and consumed it at the next
model call without another human prompt. Its history cannot distinguish a
same-run continuation from an immediate successor at that boundary. Neither
observation establishes a new delivery defect. Idle notice wake and managed
lane Runs were observed. Cross-host transfer (U7) and native macOS tests were
not run; this is not full-matrix acceptance.

## Unknown-transfer clarification and remaining acceptance

Both SDKs now use `unknown_transfer` for a locally missing binding and for a
retained-ended binding after the existing checks. Existing path, field, role
and overwrite checks keep their current precedence and
`transfer_binding_conflict` refusals.

With a v0.5.16 local daemon, the kit negotiates `unknown_transfer` for status
of an inaccessible, absent or ended transfer. Older daemons retain the legacy
`transfer_failed` response. The hello result, federation errors and wire
Accept/Cancel behavior are unchanged. An unknown live status is not an outcome
or permission to retry: terminal notices and destination hashes remain the
outcome evidence. Against older daemons the optional hello info key appears
as ordinary public peer metadata.

The earlier native observations above remain tied to e36e; they are not new
kit16 runs. U1–U5 are intended to carry through unchanged product code and the
reviewed kit delta. Fresh kit16 interactive and lane U6 checks are NOT RUN:
interactive absent status followed by same-session list/send; lane native tool
result followed by collection/ack of its observed terminal and a continuity
Run on that same lane. The model's interpretation is an observation, not a gate.
No full-matrix or native macOS claim follows.
